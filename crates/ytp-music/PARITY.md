# ytp-music parity with the Python app

`ytp-music` is a pure-Rust port of `app/ytpmv` from the Python app. Everything
is checked against output captured from that Python code
(`tests/golden/audio/*.wav`, `tests/golden/audio.json`, `tests/golden/pitch.json`
from `tools/golden/capture.py`) plus extra fixtures generated by
`crates/ytp-music/tools/gen_fixtures.py` into `crates/ytp-music/tests/fixtures/`.

Run: `cargo test -p ytp-music` (all of it), `cargo bench -p ytp-music --bench render`.

## Result summary

| area | test | result |
|---|---|---|
| nes, gb, sms, sid, opl2, opl3, ym2612, snes | `tests/parity_chips.rs` | **exact**: every 16-bit sample equal (0 LSB, 0 samples differ); length equal; peak/rms/dc within 2e-9 of `audio.json` |
| drums (6 hits, 5 chips' kits) | `tests/parity_drums_master.rs` | **exact** |
| master (`finish`: loudness gate, gain, lookahead limiter) | `tests/parity_drums_master.rs` | **exact** 16-bit samples; LUFS within 1e-3 of the recorded value |
| pitch detect / track / midi helpers (`pitch.json`) | `tests/parity_pitch.rs` | f0, stability, voiced ratio, frame counts: abs error ≤ 1e-6; stats of the PSOLA and tape renders ≤ 1e-6 |
| PSOLA with held vowel, marks, raw mode | `tests/parity_extra.rs` | marks identical integers; periods/peak 1e-9; render peak/rms/dc and 64 probe samples ≤ 1e-5 relative |
| drum shaping (`drums.shape`, onset, hiss) | `tests/parity_extra.rs` | onset/hiss/start identical; waveforms ≤ 2e-4 relative (see below) |
| MIDI parse (`music.parse`) | `tests/parity_extra.rs` | parts, roles, names, pans, notes, key, bpm, description identical |
| loudness/balance/ride/limit/envelope | `tests/parity_extra.rs` | ≤ 1e-9 (envelope 1e-6) |
| numpy primitives (sum/mean/std, linspace, hanning, interp, `default_rng().standard_normal`, float32 rfft) | `tests/parity_extra.rs` | bit-identical |

### Why the synths are exact

Floating-point order matters at the 16th bit, so the port reproduces numpy's
behaviour rather than just the maths:

* `np::sum_f32/sum_f64` are numpy's pairwise summation (8 accumulators, blocks
  of 128); `mean`/`std` use them.
* float32 vs float64 promotion follows the Python line by line (e.g. a float32
  buffer times a Python float stays float32, times a float64 envelope becomes
  float64; `float32 - float32.mean()` stays float32).
* `np::rfft_f32`: numpy 2 returns complex64 for float32 input but does the
  transform in double precision and rounds the result; same here.
* `np.interp`, `np.linspace`, `np.hanning`, `np.round` (ties to even) are
  re-implemented with the same operation order.
* `np::Rng` is numpy's `default_rng`: SeedSequence mixing, PCG64 XSL-RR and the
  ziggurat normal (tables from numpy's `ziggurat_constants.h`). The only
  randomness anywhere is the YM2612's noise drums (fixed seeds 7, 11, 13) and
  it matches for every tested seed, including seeds > 2^32.
* Complex division for the SID/GB/OPL filter responses follows numpy's Smith
  algorithm (`gb::cdiv`).

### Tolerances (the non-exact ones)

* **Drum shaping** is not in the 16-bit golden set directly; `drums.json`
  compares peak, RMS, DC and 64 probe samples. The Python FFTs float32 audio
  and uses float32 `tanh`; the Rust keeps some intermediate values in double,
  so waveforms agree to ≤ 2e-4 relative (the test asserts 2e-4; it was not measured tighter). Onsets, hiss spans
  and start positions are identical integers.
* **Pitch** (`pitch.json`): YIN runs in float64 in both. f0/stability tolerances
  are 1e-6 absolute; the PSOLA and tape renders
  agree to 1e-6 on peak/RMS/DC, and the re-detected pitch of the rendered audio
  to 1e-6.
* The `music` fixture (`song.mid`) is generated with mido and read by `midiread`;
  note times compare at 1e-12.

## What is not ported

* `pitch.decode_audio` / `loudness(path, ...)` (ffmpeg process wrappers). The
  crate takes sample slices; decoding belongs to `ytp-media`.
* (Now ported) `music._repair` / `_unoverflow` and mido's clamping of data
  bytes > 127: the MIDI reader is `midiread.rs` (mido's rules, not midly, which
  is no longer a dependency); tests in `tests/midi_overflow.rs`. `_salvage` is
  ported with it.
* `tone.SynthCache`, `nes._DPCM_CACHE`, `Voice._cache` (memoisation only;
  callers can cache on their side), `tone.catalogue()` (JSON for the web page).
* `samples.py`, `render.py`, `recommend.py`, `screen.py`, `scope.py`: they are
  corpus / video / database orchestration, not synthesis, and live in the
  `ytp-ytpmv` crate. The pure helpers that
  `render.py` uses for routing are in `routing.rs` (`which_chip`, `chip_tone`,
  `bass_line`, `floor_hz`, `octaves_to_fit`).
* `dsp.py` is ported and unit-exercised through the mastering path (K-weighting)
  but `snap_to_zero_crossing`, `haas_widen`, `fade_edge`, `downsample_4x` and the
  other helpers have no golden fixtures; they follow the Python line by line.
* The PSOLA `formant` argument is exposed internally (`formant_correct`), but
  as in Python `render()` never passes anything but 1.0.

## Speed (release, one thread, Windows 11)

Realtime factor = seconds of audio produced / wall-clock seconds, for the
4-note parity sequence (SNES: 2 notes), from `cargo bench -p ytp-music --bench render`:

| chip | realtime factor |
|---|---|
| nes | ~59x |
| gb | ~65x |
| sms | ~89x |
| sid | ~36x |
| opl2 | ~68x |
| opl3 | ~61x |
| ym2612 | ~25x |
| snes | ~240x |
| drums.shape | ~99x |
| pitch.detect | ~34x |
| psola render | ~457x |
| master.finish (stereo) | ~205x |

(Audio length includes the tails/echo that each chip returns.)
